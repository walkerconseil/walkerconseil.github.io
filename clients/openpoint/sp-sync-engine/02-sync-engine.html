00From Importer To Sync Engine

The legacy Hive/SP importer was an arm's-length implementation. The evolved ask was for a re-imagined integration: "Open in Analytics" from Social Point should feel like one click. Making it trustworthy required a new connection between two independent production systems.

The Sync Engine delivers that supported connection. A signed action establishes trust and creates or resumes the connected workspace. Metadata workflows converge its structure and access; selected-tool workflows then reconcile one proven source scope and its files into Converlens.

One connected lifecycle, four acts

Connection establishment creates the analytical context. A selected-tool operation then proves one source scope, performs an atomic canonical apply and carries remaining work to an explicit outcome.

  2. Converge workspace metadata and access
  3. Bind one Site to one connector
ACT 02 · ACQUIRE

  1. Refresh the complete catalogue
  2. Revalidate the marked target

  1. Conform and plan
  2. Transfer and stage required files

  1. Persist warnings and finalisation
  2. Clean staged or removed objects
  3. Terminalise the operation

03Adapters Plan, The Kernel Commits.

Tool-specific structure and file preparation remain with the adapter. Canonical submission-row mutation stops at one clear boundary: the adapter explains the source, and the kernel applies that plan.

Each adapter starts with a complete source snapshot. It validates that payload, maps it into a canonical shape, and compares it with the destination state. The planner then expresses the exact work as explicit create, update and remove operations. No adapter writes submission rows directly.

04Snapshot As The Safety Boundary

Each selected source scope is acquired as one bounded snapshot, validated as a whole, then turned into one controlled native change plan.

The integration audit found no generic incremental contract capable of proving complete selected-scope state across relationship-only changes, equal-precision updates, backdated writes, hard deletes and moving source data. The bridge therefore accepts one complete bounded snapshot, validates it, and turns valid evidence into an explicit plan. Tool-specific conformance may preserve existing values when a source field remains uncertain; the resulting native plan is what the kernel applies atomically.

Accepted source contract

  • One complete selected-tool scope
  • No paging or partial reconciliation
  • Oversized sources remain unsupported at that scope

Converlens guarantees

  • No deletion inferred from partial evidence
  • One explicit owned change plan
  • No partial canonical submission apply
Separate file limits: selected media is bounded independently to 1,000 files, 1 GiB cumulatively and 25 MiB per file. Catalogue responses use their own limits.

Proof before removal

A missing record means absent only within a proven complete scope. That turns reconciliation from a best-effort import into a source-owned decision.

Clean state after removal

Once absence is proven, canonical removal and its committed finalisation intent clear source-owned derived state that database cascades do not comprehensively cover, while preserving relationships that remain meaningful.

Durable recovery

Object storage cannot roll back with PostgreSQL. The design therefore combines atomic native state with persisted intent and compensating cleanup.

Durable while recovery remains active: per-file state, bounded attempts, warnings and staging pointers remain persisted while transfer, retry, finalisation or cleanup requires them. Detailed recovery rows may retire after cleanup.

Private by default. Provenance by design.

The Social Point file transport validates the exact source occurrence before transfer or deletion, retains shared objects, and does not send the provider bearer token when fetching the provider-issued HTTPS location.

06Atomic Where It Must Be. Durable Across The Whole Operation.

The complete sync is not one database transaction. It is a staged operation whose critical Social Point submission apply is atomic and whose surrounding work is persisted, bounded and recoverable.

Atomicity protects the native submission decision. Operation state protects the catalogue refresh, file transfers, warnings, deferred finalisation, compensating cleanup and terminal outcome that necessarily happen across separate transactions and external systems.

Atomic canonical submission state

  • Owned Social Point creates, updates and removals
  • Counts, hashes and immediate email and location projections
  • SP removal records and their durable finalisation intent

Durable surrounding operation

  • Previously committed catalogue state and revalidated target
  • File ledger, retries, warnings and staged storage objects
  • Deferred removal aggregates, retained relationships and cleanup
  • Explicit success, warning or failure terminalisation
Scope of the guarantee: transactional job coupling here applies to canonical Social Point mutation and removal work. It does not claim that interactive submission follow-up or the entire selected-tool operation shares the same transaction.
Future evolution, not current scope: a better Social Point source-change contract could replace acquisition while preserving the conformance, planning and kernel boundary.
