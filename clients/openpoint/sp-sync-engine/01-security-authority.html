Security & Authority

One click for the user. No implicit trust underneath.

Open in Analytics looks like a simple handoff, but it activates a fourteen-step protocol across four actors. Trust is split, the SP provider credential stays off the browser, stored provider authority is KMS-encrypted and identity-bound, and three independent gates must align before customer data can move. The result is a connection in which no single handoff, credential or configuration value can authorise the complete flow alone.

01The Three-Gate Model

Social Point capability and a given customer's access to it are deliberately separated into three activation gates of different speed, scope and blast radius. All three must be simultaneously true; none of them can compensate for an absent one. The handshake then applies request-time hard gates before work may proceed.

Three activation gatesCan this Site participate?

Capability must be deployed, cluster trust configured and the Site currently entitled.

Protocol hard gatesMay this request proceed?

Signed initiation, actor eligibility and current Site entitlement are checked at the boundaries that use them.

GATE 1 · everywhere

Generic capability

Connector code ships to every Converlens, Social Point API and Hive deployment, dark. It is inert by default, safe to deploy without a single cluster or customer being able to use it.

CL · SP API · SP Core · SP GitOps
GATE 2 · per deployment

Cluster trust

One convention-driven Vault record (the Hive signing key) plus per-cluster Git config make one API/Hive deployment able to participate at all. The signing seed is the only new integration-specific secret that operators configure for cluster trust.

<cluster>/data/<env>/converlens
GATE 3 · per customer

Site entitlement

A single audited boolean, restricted to central operations staff, per Social Point Site. This is the fast, reversible, day-to-day lever; cluster-wide activation deliberately is not.

“Only the Hive signing seed adds a new operator-configured secret to cluster trust. The issuer, edge, audience, endpoint URLs, key ID and public key remain plain, reviewable Git configuration.”

That split is what keeps the secret surface small without treating security-critical configuration as secret. The signing seed lives behind a purpose-built secret store; issuer, edge, audience, endpoint URLs, key ID and public key remain reviewable in Git. The runtime protocol still creates or uses protected bearer material, including the exchange code, provider credential, single-use handoff and resulting CL session.

02The Handshake

One click in Social Point, Open in Analytics, triggers fourteen steps across four actors. The SP provider credential remains backend-to-backend throughout. SP Core relays a five-minute, single-use handoff to the browser, but never receives the CL session created when the browser redeems it.

Two properties are structural, not incidental:
      SP Core holds the signing seed but never touches customer data directly. It can only request a link.
      SP API brokers the actual data credential per request and never sees CL's session. A compromise of any single
      hop does not hand over the others.


    
03Defence In Depth

    
Five mechanisms carry the actual weight of the handshake above. Each is backed by real code,
      several by a regression test that fails the build if the guarantee regresses.


    

      
01 · Ordering

      
CL EDGE

      
Verify before anything: not just before mutation, before any network activity

      
The signature is checked before a single DNS lookup or outbound HTTP call happens. This closes the door
        on unauthenticated probing of the callback path entirely. An attacker with a malformed token never gets
        CL to reveal that a Core origin even resolves.

      
Verification decides whether networking begins. The transport then constrains
        exactly where it may go. CL resolves the signed canonical origin and applies the complete callback
        profile before accepting a response.

      

        
Public IPs onlyReject the complete DNS result otherwise

        
Fixed routeCanonical origin, path and port

        
IP pinnedVerify the connected remote address

        
TLS verifiedNormal CA and hostname checks

        
No chainingNo redirects or retries

        
BoundedTime and response-size limits

      

      

        
        
      

      
The signature is checked first. A bad signature
        never reaches the DNS resolver or the HTTP client at all.

      
A malformed or unsigned init request could reach
        DNS and outbound HTTPS using unverified request data before anyone checks who's asking.

02 · Blast radius

      

        CL EDGE
        BROWSER
      

      
The SP provider credential never reaches the browser

      
SP Core receives and relays a 5-minute, single-use handoff, but never receives the resulting CL session.
        The browser obtains the handoff through a URL fragment, which is excluded from the initial navigation
        request and scrubbed from browser history before the application bundle loads. It then redeems the
        handoff directly with CL. The relay page on Social Point's side is CSP-pinned to one exact inline script, so
        nothing else can execute in that response.

      

        
        
      

      
The browser receives only a short-lived handoff
        from SP, scrubs it before the app loads, then redeems it directly with CL for the resulting session.

      
A long-lived credential riding through the browser
        would land in browser history, proxy logs, and Referer headers, recoverable long after the click.

03 · Rotation without downtime

      
CL EDGE

      
Multi-issuer, multi-key trust

      
Converlens supports multiple issuers, each with its own provider origin and a non-empty set of unique,
        overlapping public keys; the schema imposes no fixed maximum on either array. Verification looks up issuer
        first, key ID second. There's no "previous key" slot, live discovery or autonomous rotation service.
        Rotation is an ordered process: publish the new public key, begin signing with it, then remove the old key
        once old signatures have aged out.

      

        
        
      

      
Overlapping keys let the new key go live before
        the old one is retired: no downtime or atomic cutover.

      
Rotating the signing key would need a hard
        cutover, a window where either the old key is suddenly untrusted or the new key isn't trusted yet.

      common/models/platforms/socialpoint/link.ts:46
      
const SocialPointLinkInitIssuerSchema = z.object({

04 · Encrypted, and to exactly one place

      
CL EDGE

      
KMS-encrypted, cryptographically bound to identity

      
CL never persists a plaintext SP credential. It encrypts the credential directly with Google Cloud KMS and
        stores the ciphertext with its exact KMS key version. CRC32C protects the plaintext, ciphertext and
        authenticated-data exchanges with KMS. The authenticated data is bound to six identity values, so changing
        the edge, workspace, issuer, Site, provider connection or provider key causes decryption to fail.

      

        
        
      

      
Each ciphertext is welded to one exact connector
        identity. Decrypting it against a different workspace, Site, or key fails, even with raw database access.

      
KMS would still protect credential
        confidentiality, but ciphertext could be relocated or substituted between connector identities without a
        cryptographic identity check.

✓ direct KMS encryption + identity-bound AAD, not a shared application-level secret

    


    

      
05 · Source and destination authority

      

        CL EDGE
        SP API
      

      
A boundary enforced by schema, not by convention

      
SP owns source truth. CL owns every destination mapping and mutation decision. That boundary isn't a
        naming convention or a code-review rule. Strict Social Point wire schemas reject unknown and
        destination-only fields before accepted payloads reach business logic. A CL-only concept such as a block
        type, native ref, contact instruction or skip_nlp therefore fails parsing at the contract
        boundary. Committed contract tests demonstrate that rejection; the absence of matching CL vocabulary in SP
        API provides supporting evidence that destination decisions remain on the CL side.

      

        
        
      

      
Strict parsing rejects unknown or destination-only
        fields before the accepted request reaches business logic.

      
A bug, or a compromised SP deployment, could
        smuggle a CL-only instruction into what's meant to be pure source data, and CL would have no structural
        reason to reject it.

      common/models/platforms/socialpoint/contracts.spec.ts:108

expect(() => Schema.parse({ ...fixture, blocks: [] })).toThrow()        // CL concept

05What the Model Guarantees

    
The assurance comes from explicit boundaries that can be named and tested. Restraint keeps those
      boundaries reviewable instead of surrounding them with new mutable authorities.


    

      
Trust before networkInvalid initiation cannot trigger DNS or HTTP.

      
Authority remains dividedNo handoff, credential or configuration value authorises the complete flow alone.

      
Entitlement remains liveEvery provider request checks the current Site decision.

      
Provider credential stays backend-onlyThe browser sees a handoff and CL session, never the SP credential.

      
Ciphertext stays identity-boundKMS decryption fails outside the exact connector identity.

      
Wire authority stays narrowStrict parsing rejects destination-only instructions.

    


    

      

        
Deliberately not automated

        
    
          
  • Signing trust is per deployment, not a per-Site key registry or certificate system.
    • 
          
  • Rotation uses explicit key overlap, not autonomous discovery or scheduling.
    • 
          
  • Issuer, callback and CL authority come from reviewed configuration, not source-selected values.
    • 
          
  • Replay protection uses Core exchange state and CL's expiring, single-use handoffs, not another nonce store.
    • 
          
  • AVP supplies the secret boundary; no second optional-secrets controller is introduced.
    • 
          
  • Disablement remains reversible; explicit, separately authorised offboarding performs revocation.
    • 
        

      

      

        
Why the restraint matters

        
    
          
  • Fewer mutable authorities and fewer paths that can silently expand access.
    • 
          
  • A smaller secret and operational surface, built on mechanisms the platforms already operate.
    • 
          
  • Clear activation, rotation, disablement and revocation paths that remain visible to reviewers.
    • 
        

      

    


    

      
The security model, in one sentence

      
Trust is established before action, authority is incomplete in every one place, and access remains
        reversible at the boundary where customer data is served.
